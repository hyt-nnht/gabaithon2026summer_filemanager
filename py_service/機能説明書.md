# Pythonファイル解析サービス 機能説明書

## 1. 概要

このサービスは、ローカルに保存されたPDFまたは画像から文字を抽出し、文書の種類・発行元・日付を推定するPython製のHTTP APIです。C#側のファイル整理アプリから呼び出すことを想定しています。

現在の実装は、ハッカソン用の最小構成です。解析結果と推奨ファイル名を返しますが、元ファイルの移動・改名・削除は行いません。実際の整理処理と、結果を採用するかどうかの判断は呼び出し側が担当します。

主な構成は次のとおりです。

| 機能 | 使用技術 | 役割 |
|---|---|---|
| テキストPDF解析 | `pypdf` | PDF内の既存テキスト層を抽出 |
| 画像・スキャンPDF解析 | `RapidOCR`、`ONNX Runtime` | 画像から文字を認識 |
| PDF画像化 | `pypdfium2` | スキャンPDFをOCR用画像へ変換 |
| 規則分類 | Pythonのキーワード判定 | 常に利用できる最低限の分類結果を生成 |
| SLM分類 | `llama-cpp-python`、Gemma-2-2B-it GGUF | 文脈を考慮して分類結果を補正 |
| HTTP API | FastAPI、Uvicorn | C#など別プロセスから機能を利用可能にする |

## 2. 対応する入力

対応形式は次の4種類です。

- PDF（`.pdf`）
- PNG（`.png`）
- JPEG（`.jpg`、`.jpeg`）

既定のファイルサイズ上限は20 MiBです。解析対象は`ANALYZER_ALLOWED_ROOT`で指定したディレクトリの内部に存在する必要があります。

暗号化PDFと上記以外の形式には対応していません。

## 3. 処理の流れ

1. 解析対象が存在するか、許可ディレクトリ内か、サイズ上限内かを確認します。
2. PDFまたは画像からテキストを抽出します。
3. 抽出テキストと元ファイル名を規則ベースで分類します。
4. `slm_with_rules_fallback`の場合は、規則結果と抽出テキストをGemmaへ渡して再分類します。
5. SLMが正常ならSLM結果を採用し、不明な発行元・日付だけ規則結果で補います。
6. SLMを使用できない場合は規則結果を採用し、`partial`として警告を返します。
7. 文書種別、発行元、日付、推奨ファイル名をJSONで返します。

同時に複数の解析要求を受けた場合、OCRとSLMによる重い処理はサービス内で直列に実行されます。

## 4. テキスト抽出

### 4.1 テキストPDF

PDFでは、最初に必ず`pypdf`でテキスト層を読み取ります。空白・改行などを除いた有効文字数が既定で50文字以上なら、そのテキストを採用してOCRは実行しません。

抽出対象は既定で先頭10ページまでです。実際の総ページ数は解析結果の`page_count`へ返します。

### 4.2 スキャンPDF

`pypdf`の抽出結果が50文字未満、またはテキスト抽出に失敗した場合は、`pypdfium2`でPDFを画像化してRapidOCRを実行します。

既定では先頭3ページまでを約180 DPI相当で処理します。この場合、抽出元を表す`source`は`rapidocr_pdf`になります。

### 4.3 PNG・JPEG

画像ファイルはRapidOCRで直接処理します。抽出元を表す`source`は`rapidocr`です。文字が1文字も得られない場合は解析失敗になります。

### 4.4 抽出結果

APIは抽出全文を返さず、既定では先頭1,000文字だけを`text_preview`として返します。主な項目は次のとおりです。

| 項目 | 内容 |
|---|---|
| `source` | `pypdf`、`rapidocr`、`rapidocr_pdf`のいずれか |
| `text_preview` | 抽出テキストの先頭部分 |
| `character_count` | 抽出した文字数 |
| `confidence` | OCRの平均信頼度。`pypdf`では`null` |
| `page_count` | 元PDFの総ページ数。画像では1 |
| `elapsed_ms` | テキスト抽出に要した時間 |

## 5. 文書分類

分類結果の`document_type`は次の5種類です。

| 値 | 意味 | 主な規則キーワード |
|---|---|---|
| `receipt` | 領収書・レシート | 領収書、領収証、合計、税込、お預り、現金 |
| `invoice` | 請求書 | 請求書、請求金額、支払期限、お支払期限、振込先 |
| `meeting_minutes` | 議事録 | 議事録、出席者、議題、決定事項 |
| `contract` | 契約書 | 契約書、甲、乙、契約期間、署名 |
| `other` | その他 | 上記に該当するキーワードがない文書 |

### 5.1 規則ベース分類

抽出テキストと元ファイル名に含まれるキーワードを数え、最も一致数が多い種別を選びます。同点の場合の優先順は`receipt`、`invoice`、`meeting_minutes`、`contract`です。

日付は`2026年9月1日`、`2026-09-01`、`2026/09/01`、`2026.09.01`のような表記から、最初に見つかった実在日を`YYYY-MM-DD`形式へ変換します。

発行元は「発行元:」「発行者:」「請求元:」「販売元:」「会社名:」などの表記、または株式会社・有限会社・合同会社・Inc.・LLCを含む名称から抽出します。

### 5.2 SLM分類

SLM分類には仕様書v3.6で指定された`gemma-2-2b-it-Q4_K_M.gguf`を使用します。Gemmaには次の情報を渡します。

- 元ファイル名
- 規則ベースの分類候補
- 抽出テキストの先頭4,000文字
- 使用できる文書種別とJSON出力条件

SLM出力は、文書種別・発行元・文書日付・信頼度・理由を持つJSONとして検証します。日付など任意項目の値が不正な場合、その項目を`null`として扱い、規則結果で補完します。文書種別が不正、必須キーがない、余分なキーがあるなど、分類結果として利用できない場合は規則分類へフォールバックします。

### 5.3 最終結果と推奨ファイル名

SLMが成功した場合、最終的な文書種別にはSLM結果を使います。SLMで発行元または日付が得られなかった場合は、その項目だけ規則結果を使います。

推奨ファイル名の形式は次のとおりです。

```text
YYYY-MM-DD_発行元_文書種別
```

例:

```text
2026-09-01_デモソリューション株式会社_請求書
```

日付または発行元を取得できなかった場合は、それぞれ`日付不明`、`発行元不明`になります。Windowsでファイル名に使用できない記号は`_`へ置換します。拡張子は付けないため、実際に改名する側で元の拡張子を維持してください。

## 6. 解析モードとフォールバック

`POST /v1/analyze`の`analysis_mode`には次の値を指定できます。

| 値 | 動作 |
|---|---|
| `slm_with_rules_fallback` | 規則分類後にSLMを実行。失敗時は規則結果を返す（既定） |
| `rules_only` | SLMを実行せず規則結果だけを返す |

正常時の`status`は`success`です。SLMが未設定、モデルのロードに失敗、または出力JSONが不正だった場合も解析全体は中止せず、規則結果を`status: partial`、`fallback_used: true`として返します。

## 7. セットアップ

Python 3.11以上を使用します。リポジトリのルートで次を実行します。

```bash
python3 -m venv py_service/.venv
./py_service/.venv/bin/python -m pip install --upgrade pip
./py_service/.venv/bin/python -m pip install -e 'py_service[ocr,slm,dev]' \
  --extra-index-url https://abetlen.github.io/llama-cpp-python/whl/cpu
```

すでにOCRと開発用パッケージを導入済みなら、SLM関連だけを追加できます。

```bash
./py_service/.venv/bin/python -m pip install -e 'py_service[slm]' \
  --extra-index-url https://abetlen.github.io/llama-cpp-python/whl/cpu
```

Gemmaモデルは別途取得します。

```bash
mkdir -p py_service/models
./py_service/.venv/bin/hf download \
  bartowski/gemma-2-2b-it-GGUF \
  gemma-2-2b-it-Q4_K_M.gguf \
  --local-dir py_service/models
```

## 8. 起動と動作確認

リポジトリのルートで環境変数を設定して起動します。

```bash
export ANALYZER_SLM_MODEL=/home/rdoki/projects/gabaithon26sm/py_service/models/gemma-2-2b-it-Q4_K_M.gguf
export ANALYZER_ALLOWED_ROOT=/home/rdoki/projects/gabaithon26sm
./py_service/.venv/bin/python -m file_analyzer --host 127.0.0.1 --port 8765
```

別のターミナルから状態確認とウォームアップを実行します。

```bash
curl http://127.0.0.1:8765/v1/health
curl -X POST http://127.0.0.1:8765/v1/warmup
```

`health`で`ocr_available`、`pdf_available`、`slm_available`がすべて`true`なら必要な機能を利用できます。`warmup`で`ocr_ready`と`slm_ready`がともに`true`なら、OCRエンジンとモデルを実際にロードして推論できています。

CPU環境ではSLMの初回ロードと推論に数十秒かかる場合があります。呼び出し側のHTTPタイムアウトは30秒以上を目安にしてください。

## 9. API

APIはローカルホストだけで待ち受けます。Swagger UIは次のURLで確認できます。

```text
http://127.0.0.1:8765/docs
```

### 9.1 `GET /v1/health`

依存パッケージとSLMモデルの利用可否を返します。実際のOCR・推論処理は行いません。

レスポンス例:

```json
{
  "status": "ready",
  "service_version": "0.1.0",
  "ocr_available": true,
  "pdf_available": true,
  "slm_available": true,
  "slm_model": "gemma-2-2b-it-Q4_K_M.gguf"
}
```

### 9.2 `POST /v1/warmup`

OCRエンジンをロードし、サンプル請求書を使ってSLM推論まで実行します。

レスポンス例:

```json
{
  "ocr_ready": true,
  "slm_ready": true,
  "elapsed_ms": 20272,
  "warnings": []
}
```

### 9.3 `POST /v1/analyze`

指定したローカルファイルを解析します。`file_path`はPythonサービスから参照できる絶対パスを指定してください。

実行例:

```bash
curl -X POST http://127.0.0.1:8765/v1/analyze \
  -H 'Content-Type: application/json' \
  -d '{
    "schema_version": "1.0",
    "job_id": "demo-001",
    "file_path": "/home/rdoki/projects/gabaithon26sm/請求書_デモ.png",
    "analysis_mode": "slm_with_rules_fallback",
    "language": "ja"
  }'
```

リクエスト項目:

| 項目 | 必須 | 内容 |
|---|---|---|
| `schema_version` | 省略可 | 現在は`1.0`のみ。既定値も`1.0` |
| `job_id` | 必須 | 呼び出し側が付けるジョブ識別子 |
| `file_path` | 必須 | 解析対象の絶対パス |
| `expected_size` | 省略可 | 読み取り前に照合するファイルサイズ |
| `expected_last_write_utc` | 省略可 | 読み取り前に照合する更新日時 |
| `analysis_mode` | 省略可 | SLM併用または規則のみ。既定はSLM併用 |
| `language` | 省略可 | `ja`または`en`。現在の分類規則とSLM指示は日本語向け |

レスポンス例:

```json
{
  "schema_version": "1.0",
  "job_id": "demo-001",
  "status": "success",
  "extraction": {
    "source": "rapidocr",
    "text_preview": "請求書\n発行元: デモソリューション株式会社",
    "character_count": 78,
    "confidence": 0.96,
    "page_count": 1,
    "elapsed_ms": 2900
  },
  "baseline": {
    "document_type": "invoice",
    "organization": "デモソリューション株式会社",
    "document_date": "2026-09-01"
  },
  "ai_suggestion": {
    "document_type": "invoice",
    "organization": "デモソリューション株式会社",
    "document_date": "2026-09-01",
    "confidence": 0.98,
    "reason": "請求書、請求金額、支払期限が記載されている"
  },
  "final_decision": {
    "decision_source": "slm",
    "document_type": "invoice",
    "organization": "デモソリューション株式会社",
    "document_date": "2026-09-01",
    "destination_key": "invoice",
    "suggested_base_name": "2026-09-01_デモソリューション株式会社_請求書"
  },
  "fallback_used": false,
  "warnings": [],
  "error": null,
  "elapsed_ms": 23000
}
```

`expected_size`または`expected_last_write_utc`を指定すると、解析開始までにファイルが更新されていないか検出できます。

## 10. 認証

`ANALYZER_BEARER_TOKEN`を設定すると、すべてのAPIでBearer認証が必要になります。

```bash
export ANALYZER_BEARER_TOKEN=demo-secret
curl http://127.0.0.1:8765/v1/health \
  -H 'Authorization: Bearer demo-secret'
```

トークンを設定しない場合は認証なしで利用できます。サービス自体は`127.0.0.1`または`localhost`以外では起動できません。

## 11. 主な環境変数

| 変数 | 既定値 | 内容 |
|---|---:|---|
| `ANALYZER_ALLOWED_ROOT` | 起動ディレクトリ | 読み取りを許可するルート |
| `ANALYZER_BEARER_TOKEN` | 未設定 | APIのBearerトークン |
| `ANALYZER_MAX_FILE_BYTES` | `20971520` | 最大ファイルサイズ（byte） |
| `ANALYZER_MAX_PDF_PAGES` | `10` | `pypdf`で抽出する最大ページ数 |
| `ANALYZER_MIN_PDF_TEXT_CHARS` | `50` | テキストPDFと判断する最小有効文字数 |
| `ANALYZER_MAX_OCR_PDF_PAGES` | `3` | PDFをOCRする最大ページ数 |
| `ANALYZER_PDF_RENDER_SCALE` | `2.5` | OCR時のPDF画像化倍率 |
| `ANALYZER_SLM_MODEL` | 未設定 | GGUFモデルの絶対パス |
| `ANALYZER_SLM_CONTEXT_SIZE` | `4096` | SLMのコンテキスト長 |
| `ANALYZER_SLM_THREADS` | 自動 | CPU推論スレッド数 |
| `ANALYZER_SLM_MAX_TOKENS` | `384` | SLMの最大出力トークン数 |
| `ANALYZER_SLM_UNLOAD` | `true` | 各推論後にモデルをメモリから解放するか |

複数ファイルを続けてデモする場合、次の設定でモデルをメモリ上に保持できます。2件目以降のモデル再ロードを避けられますが、サービス停止までメモリを使用します。

```bash
export ANALYZER_SLM_UNLOAD=false
```

## 12. エラーと警告

主なエラーコードは次のとおりです。

| コード | 内容 |
|---|---|
| `FILE_NOT_FOUND` | ファイルが存在しない、またはファイルではない |
| `PATH_NOT_ALLOWED` | 許可ルート外のファイルを指定した |
| `FILE_TOO_LARGE` | ファイルサイズが上限を超えた |
| `FILE_CHANGED` | 指定したサイズまたは更新日時と一致しない |
| `UNSUPPORTED_TYPE` | PDF、PNG、JPG、JPEG以外を指定した |
| `PDF_ENCRYPTED` | 暗号化PDFを指定した |
| `PDF_EXTRACTION_FAILED` | PDFのテキスト抽出に失敗した |
| `OCR_FAILED` | OCRに失敗した、または文字を抽出できなかった |
| `SLM_UNAVAILABLE` | モデル・依存関係・推論の問題でSLMを利用できない |
| `INVALID_MODEL_OUTPUT` | SLMの出力を分類結果として検証できない |

PDFのテキスト抽出からOCRへ切り替えた場合は、成功レスポンス内の`warnings`に`PDF_TEXT_LAYER_INSUFFICIENT`または`PDF_TEXT_EXTRACTION_FAILED`が入ります。

## 14. 現在の制限

- 対応する分類は`receipt`、`invoice`、`meeting_minutes`、`contract`、`other`だけです。
- 規則分類は単純なキーワード出現数であり、高度なレイアウト解析はしません。
- 日本語PDFでは、PDF内部の文字配置によって`pypdf`の抽出テキストに不自然な改行が入る場合があります。
- テキスト層が50文字以上あるPDFはOCRへ切り替えないため、テキスト品質が低くても`pypdf`結果を使用する場合があります。
- スキャンPDFのOCRは既定で先頭3ページだけです。
- SLMへ渡すテキストは先頭4,000文字だけです。
- CPUでのSLM推論には数十秒かかる場合があります。
- `language`はAPI互換用に受け取りますが、現在の規則キーワードとSLMプロンプトは日本語向けです。
- このサービスは分類候補を返すだけで、ファイル操作や永続的な履歴保存は行いません。

これらはハッカソン用の最小実装として意図した制限です。まず分類デモを成立させ、必要になった項目だけ後から改善する方針です。
